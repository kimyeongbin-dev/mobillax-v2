# 보안 규칙

기능을 고치거나 늘려도 **깨지면 안 되는 보안 규칙**과, 각 규칙을 지키는 회귀 테스트를 정리합니다. 규칙은 테스트로 고정되어 있어서, 어기는 변경은 `docker compose --profile test run --rm --build test`에서 실패합니다.

- 회귀 테스트를 지우거나 약하게 바꾸지 않습니다. 규칙 자체를 바꿔야 하면 이 문서와 테스트를 같은 PR에서 고치고, PR 본문에 이유를 적습니다.
- 새 API를 추가하면 아래 규칙에 해당하는지 확인하고 테스트에 추가합니다.

## S1. 결제 금액과 결제 완료 확인 (v2.2)

브라우저가 보낸 금액과 "결제됨" 알림은 믿지 않습니다.

1. **운임 확인 (담기·바로 결제):** 구간마다 편을 조회한 조건(교통수단·출발/도착 TAGO ID)과 고른 편(편 번호·출발 일시)을 받아, 서버가 TAGO를 다시 조회해 그 편의 운임과 같을 때만 받습니다. 편이 없거나 운임이 다르거나 당일 출발이 아니면 400입니다. 장바구니에는 확인된 항목만 `fare_verified = true`로 저장하고, 그 전에 담긴 항목은 결제하지 않습니다.
2. **결제 준비:** 서버가 금액을 합산해 결제 기록을 `PENDING`으로 먼저 남기고, 그 결제 번호·금액으로만 결제창을 엽니다.
3. **결제 완료:** 결제 번호만 받습니다. 자기 `PENDING` 기록이 없으면 404입니다. PortOne V2 결제 단건 조회(`GET /payments/{paymentId}`, API Secret은 서버에만)로 다음을 확인합니다.
   - `status = PAID`가 아니면 완료로 기록하지 않습니다 (`PENDING` 유지).
   - 금액(`amount.total`)·통화(`KRW`)·상점(`storeId`)이 준비 때 기록과 다르면 **PortOne 결제를 취소**하고 `FAIL`로 기록합니다.
   - 같은 묶음·교통수단이 이미 다른 결제로 `SUCCESS`이면 중복 결제로 보고 취소·`FAIL`합니다.
   - 모두 맞으면 `SUCCESS`로 바꾸고 장바구니 묶음을 비웁니다. 이미 `SUCCESS`인 결제는 다시 확인하지 않습니다.
4. **결제 실패 알림:** 자기 `PENDING` 기록만 `FAIL`로 바꿉니다. 새 기록을 만들거나 `SUCCESS`를 바꾸지 않습니다.
5. 마이페이지 이번 달 결제 합계는 `SUCCESS`만 셉니다.

남은 일: 결제 후 브라우저를 닫아 완료 알림이 오지 않으면 `PENDING`으로 남습니다. PortOne 웹훅으로 보완하는 것은 배포(v3) 때 다룹니다.

## S2. 로그인 필요 범위 (v2.1)

- 로그인 없이 열리는 화면: `/`, `/home`, `/login`, `/register`, `/error`, 정적 파일(`/css/**`, `/javascript/**`, `/images/**`), 그리고 v2.9부터 경로 상세·요금비교·주변정보(`/route`, `/compare`, `/nearby`)
- 로그인 없이 쓰는 API(v2.9): 경로 검색(`/api/route/transit`), 장소 매칭(`/api/place/match`), 편 조회(`/api/trips`), 주변정보(`/api/nearby`). 모두 호출 횟수를 제한합니다(S11).
- 그 밖의 화면(`/cart`, `/mypage` 등)은 로그인 페이지로 보냅니다.
- 그 밖의 `/api/**`(장바구니·세션 연장)와 `/payment/**`는 로그인하지 않으면 `401 {"error":"로그인이 필요합니다."}`를 돌려줍니다.
- 비로그인으로 연 상세 화면에는 담기·결제 버튼 대신 "로그인하고 예매하기"가 있습니다. 로그인하면 보던 화면으로 돌아옵니다(S11의 돌아갈 화면 제한).

## S3. CSRF 토큰 전달 방식 (v2.1)

- 서버는 `XSRF-TOKEN` 쿠키(HttpOnly 아님)로 토큰을 내려보냅니다.
- 폼: Thymeleaf `th:action`이 숨은 `_csrf` 필드를 넣습니다. 로그인·회원가입 폼은 `_csrf` 필드를 직접 넣습니다.
- fetch: `static/javascript/csrf.js`가 같은 사이트로 보내는 GET 이외 요청에 `X-XSRF-TOKEN` 헤더를 붙입니다. fetch를 쓰는 화면은 이 파일을 다른 스크립트보다 먼저 불러옵니다.
- 로그아웃: 헤더의 로그아웃은 POST 폼 버튼입니다.

## S4. 소유권 (v2.1)

- 장바구니 조회·삭제·결제 준비는 로그인한 사용자의 이메일 조건으로만 찾습니다. 다른 사용자의 묶음은 없는 것처럼 동작합니다.
- 예매 내역(v2.5)도 로그인한 사용자의 결제만 조회합니다(`MyPageFeatureTests.PaymentHistory`).
- **예매 내역에서 삭제(v2.5)는 화면에서만 숨깁니다.**
  - 결제 기록은 지우지 않고 `hidden_at`만 남깁니다.
    - 전자상거래법상 대금결제·공급 기록은 5년, 분쟁 처리 기록은 3년 보존 대상입니다.
    - 숨긴 기록도 중복 결제 확인(S1)과 환불·분쟁 대응에 그대로 씁니다.
    - 화면 계산(예매 내역, 마이페이지 이번 달 결제 합계)에는 넣지 않습니다. 사용자가 보는 내역과 합계가 맞아야 합니다.
  - 숨길 수 있는 것은 내 기록 가운데 내역에 보이는 상태(완료·실패)뿐입니다. 남의 기록, 준비 중 기록, 없는 번호는 같은 404이고, 형식이 틀리면 400, CSRF 토큰이 필요합니다.
  - 숨긴 내역은 사용자가 직접 다시 볼 수 없고, 고객센터 문의를 받은 관리자가 확인합니다(관리자 기능은 이후 버전).
  - 보존 기간이 지난 기록 삭제, 회원 탈퇴 시 분리 보관은 v3 운영 정책으로 다룹니다.
- **비밀번호 변경(v2.5):**
  - 현재 비밀번호가 맞아야 바꿀 수 있습니다. 로그인된 화면을 잠깐 빌린 사람이 비밀번호를 바꿔 계정을 빼앗지 못하게 하기 위해서입니다.
  - 새 비밀번호는 `@Password` 규칙을 따르고, 지금 비밀번호와 같은 값은 받지 않습니다.
  - CSRF 토큰이 필요합니다(S3).
  - 성공하면 세션 ID를 바꿔, 바꾸기 전 세션 ID가 계속 쓰이지 못하게 합니다(세션 고정 방지).
  - 현재 비밀번호를 여러 번 틀리는 시도는 호출 횟수 제한(v2.8)에서 다룹니다.
- 결제 실패 기록은 다른 사용자의 결제 번호면 404로 거절합니다(기록이 있다는 사실도 알리지 않음).
- **결제 번호 형식이 알려져도 안전합니다.** 형식 검사(S10)는 첫 관문일 뿐이고, 그 뒤에서 아래 순서로 막습니다(v2.4에서 실제 공격 시나리오로 확인).

  | 순서 | 검사                                      | 막는 공격                                                                        |
  | ---- | ----------------------------------------- | -------------------------------------------------------------------------------- |
  | 1    | 형식(`payment-...`)                       | 형식이 다른 임의 문자열                                                          |
  | 2    | 서버가 결제 준비 때 만든 기록이 있는지    | 형식만 흉내 낸 가짜 번호. 기록도 새로 만들지 않음                                |
  | 3    | 그 기록이 로그인한 사용자 것인지          | 남의 결제 번호로 완료·실패 처리 (남의 진행 중 결제를 실패로 바꿔 막는 공격 포함) |
  | 4    | PortOne 조회: 결제됨, 금액·통화·상점 일치 | 자기 번호로 결제하지 않고 완료 요청, 금액 위조                                   |
  - 2와 3은 같은 404와 같은 문구로 응답합니다. 응답만으로 어떤 번호가 존재하는지 알아낼 수 없습니다.
  - 번호의 UUID 부분은 무작위 122비트라 추측할 수 없습니다. 추측하더라도 3에서 막힙니다.
  - 남의 번호로 시도하면 PortOne을 부르지 않습니다. 외부 호출이나 한도를 쓰게 만들 수 없습니다.
  - 회귀 테스트: `S4_Ownership.cannotFailOthersPendingPaymentOrProbeIt`, `PaymentVerificationRegressionTests`(가짜 번호, 남의 번호, 미결제, 금액 불일치).

- 화면에서 쓰지 않던 장바구니 복원 API(`/payment/restore-cart`)는 지웠습니다.

## S5. 응답에 내부 정보를 넣지 않는다 (v2.3)

- 사용자에게 보여 줄 문구는 `UserFacingException`으로 던집니다. 응답(400)에는 이 예외의 메시지만 싣습니다.
- 라이브러리·프레임워크가 던진 `IllegalArgumentException`은 클래스 이름, 값 형식 같은 내부 정보가 섞일 수 있어 "요청 값이 올바르지 않습니다."로 바꾸고, 원문은 로그에만 남깁니다.
- 처리하지 못한 예외(500)는 일반 문구만 응답합니다. 로그에는 예외 종류와 메시지만 남기고, 키가 든 URL이 섞일 수 있는 스택트레이스는 남기지 않습니다.
- 스프링 기본 오류 응답도 메시지·스택트레이스·바인딩 오류·예외 이름을 넣지 않습니다(`server.error.include-*`).
- 예외 메시지를 응답에 내보내던 `/health/db`는 없앴습니다(S7).

## S6. 로그에 남기지 않는 것 (v2.3)

- SQL(`spring.jpa.show-sql`)은 콘솔에 찍지 않습니다. `.env`의 `SHOW_SQL`·`FORMAT_SQL`은 더 이상 쓰지 않습니다.
- 아래 로거는 루트 로그 수준과 상관없이 INFO로 고정합니다.
  - `org.springframework.security`: 요청·세션 정보를 남김
  - `org.hibernate.SQL`, `org.hibernate.orm.jdbc.bind`, `org.hibernate.type.descriptor.sql`: SQL과 바인드 값(개인정보, 비밀번호 해시)을 남김
  - `org.springframework.web.client`, `org.springframework.web.reactive.function.client`, `reactor.netty.http.client`: 키가 든 외부 호출 URL을 남김
- 로컬에서 SQL 문만 보려면 `SPRING_PROFILES_ACTIVE=sqldebug`를 씁니다. 이 프로필에서도 바인드 값은 켜지 않습니다.
- 요청 본문을 `System.out`으로 찍던 코드는 지웠습니다.
- 키 형태 마스킹은 로그 패턴과 `LogSecretMaskingTests`가 지킵니다(v1.x).

## S7. 헬스체크 (v2.3)

| 경로               | 확인하는 것                                            | 용도                                    |
| ------------------ | ------------------------------------------------------ | --------------------------------------- |
| `GET /health`      | DB + 외부 API(TMAP, TAGO, 카카오, 도로명주소, PortOne) | 서비스 전체 상태                        |
| `GET /health/live` | DB                                                     | 컨테이너 헬스체크(`docker-compose.yml`) |

- 로그인 없이 열리고, 응답은 `{"status":"UP"}`(200) 또는 `{"status":"DOWN"}`(503)뿐입니다. 어느 구성 요소가 왜 실패했는지는 응답에 넣지 않고 로그에만 남깁니다. `Cache-Control: no-store`입니다.
- **비로그인 사용자가 DB·외부 API를 건드릴 수 없게:**
  - DB는 연결이 유효한지만 봅니다(쿼리·데이터 없음). 결과를 5초 동안 재사용하므로 요청이 몰려도 연결 시도는 5초에 한 번입니다.
  - 외부 API는 요청 때 호출하지 않습니다. 30분마다 가벼운 호출로 점검해 둔 결과만 씁니다. 그래서 헬스체크 요청으로 외부 호출이나 한도 소모가 일어나지 않습니다.
- **외부 API 점검 방법:**
  - TAGO: 열차 도시 코드 목록
  - 카카오: 서울역 좌표 → 주소
  - 도로명주소: "서울역" 검색
  - PortOne: 없는 결제 번호 조회(404면 키 정상)
  - 한 번 실패하면 한 번 더 시도하고, 두 번 모두 실패해야 이상으로 기록합니다. 도로명주소 API는 연결의 절반가량이 시간 초과되는 때가 있었습니다.
  - **TMAP 대중교통은 하루 10건 한도라 점검 호출을 하지 않습니다.** 실제 경로 검색 결과로 판단합니다. 키 오류·한도 초과·응답 없음은 이상, 검색 결과 없음(400)은 정상입니다.
  - 아직 점검하지 않은 API는 이상으로 보지 않습니다. 키를 설정하지 않은 선택 API(카카오 REST, 도로명주소)는 점검하지 않습니다.
- **컨테이너는 `/health/live`를 씁니다.** 외부 API 장애나 TMAP 한도 소진으로 앱 컨테이너가 "unhealthy"가 되어 재시작되는 일을 막기 위해서입니다.

## S8. 컨테이너 (v2.3)

- 앱 이미지는 전용 사용자 `app`(uid 10001)으로 실행합니다. JAR은 root 소유라 앱이 자기 실행 파일을 바꿀 수 없습니다.
- MySQL 헬스체크는 앱 계정 비밀번호를 명령 인자가 아니라 `MYSQL_PWD` 환경변수로 넘깁니다. compose 파일에는 `$$MYSQL_PASSWORD`(컨테이너 안 변수 이름)만 있어 `docker inspect`에 값이 나오지 않습니다. 예전에는 `-p${DB_ROOT_PASSWORD}`로 root 비밀번호가 인자에 들어갔습니다.
- 앱 컨테이너에 `/health/live` 헬스체크를 추가했습니다.
- `scripts/infra-rules.test.js`(`npm run test:infra`)가 Dockerfile 실행 단계의 `USER`, compose 명령 인자의 비밀번호, 앱 헬스체크 경로를 검사합니다. Gradle 테스트 컨테이너에는 이 파일들이 들어가지 않아 Node로 검사합니다.
- 남은 일(v3): 앱 컨테이너는 `env_file: .env`로 쓰지 않는 값(`DB_ROOT_PASSWORD` 등)까지 받습니다. 배포 때 필요한 변수만 넘기도록 나눕니다.

## S9. 브라우저로 가는 키 (v2.3)

화면 소스·JS·응답은 사용자가 모두 볼 수 있으므로, 브라우저로 보낸 키는 숨길 수 없습니다. 그래서 키마다 **브라우저로 보내도 되도록 설계된 키인지**를 공식 문서와 콘솔 설정으로 확인하고 정했습니다.

| 키                                                           | 제공사의 보호 방식 (확인한 근거)                                                                                                                      | 결론                               |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 카카오 JavaScript 키                                         | 공식 지도 가이드가 `sdk.js?appkey=`로 브라우저에 넣음. 콘솔 설명: "등록한 도메인에서만 JavaScript 키로 Kakao SDK for JavaScript를 사용할 수 있습니다" | 브라우저 허용 (도메인 등록 필수)   |
| TMAP appKey                                                  | SK open API 콘솔: 앱마다 키 하나, 신청한 상품(TMAP, TMAP 대중교통)이 같은 키에 묶임. 제한은 **IP 허용 목록뿐**, 도메인 제한 없음                      | 서버 전용 (배포 때 서버 IP만 허용) |
| 카카오 REST 키                                               | 클라이언트 시크릿·호출 허용 IP 설정이 붙는 서버용 키                                                                                                  | 서버 전용                          |
| PortOne V2 API Secret, 공공데이터·도로명주소 키, DB 비밀번호 | 비밀값                                                                                                                                                | 서버 전용                          |
| PortOne `storeId`·`channelKey`                               | 결제창 SDK에 넘기는 식별자. 결제 확인·취소에는 쓸 수 없음                                                                                             | 브라우저 허용 (키가 아님)          |

**바꾼 것**

- 경로 지도를 TMAP 지도 SDK에서 **카카오맵**으로 바꿨습니다. TMAP이 주는 좌표가 위경도(WGS84)라 경로 선을 그대로 옮겨 그립니다. 경로 계산은 그대로 서버가 TMAP으로 합니다.
- 홈 화면이 쓰지 않으면서 불러오던 TMAP 지도 SDK를 지웠습니다. 이 때문에 **로그인하지 않은 사용자도 홈 소스에서 하루 10건 한도의 TMAP 키를 볼 수 있었습니다.**
- `FrontendKeyAdvice`는 카카오 JavaScript 키만 템플릿에 넣습니다.

**회귀 테스트 (`KeyExposureRegressionTests`)**

- 로그인 전(`/`, `/home`, `/login`, `/register`)과 후(`/route`, `/cart`, `/mypage`, `/mypage/edit`) 화면, 모든 정적 JS를 실제로 렌더링해 **실제 설정값**과 비교합니다. 서버용 키가 한 글자라도 들어 있으면 실패합니다.
- 카카오 JavaScript 키는 카카오 지도 SDK 주소 안에서만 쓰여야 합니다.
- 외부 스크립트는 카카오 지도 SDK와 PortOne SDK만 허용하고, TMAP 주소(`apis.openapi.sk.com`)는 금지합니다.
- 실패 메시지에는 키 이름과 화면 경로만 나오고, 키 값이나 본문은 출력하지 않습니다.
- 예전 코드(홈에 TMAP SDK)로 되돌려 실행하면 `서버용 키 TMAP_APPKEY 가 / 응답에 들어 있다`로 실패하는 것을 확인했습니다.

**배포(v3) 때 할 일**

- 카카오 JavaScript SDK 도메인에 운영 도메인 추가 (현재 `http://localhost:8080`만 등록)
- SK appKey의 IP 허용 목록에 서버 IP만 등록 (현재 "Any IP allowed")
- 필요하면 카카오 REST 키에도 호출 허용 IP 등록

## S10. 입력값 검증과 출력 이스케이프 (v2.4)

요청 본문, 경로, 폼 값은 개발자도구로 얼마든지 바꿀 수 있습니다. 화면의 `maxlength`, `required`, 선택 상자는 안내일 뿐이고, **서버가 모든 값을 다시 검사**합니다.

**구조 (공통 계층에서 강제)**

| 구성                                           | 역할                                                                                                                                                                                                                                                        |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Common/Validation/InputRules`, `AccountRules` | 정규식·범위·계정 규칙을 한 곳에 모음                                                                                                                                                                                                                        |
| 재사용 제약 어노테이션                         | `@TagoId`, `@TripNo`, `@DateTimeMinute`, `@DateYmd`, `@PaymentId`, `@PayableMode`, `@TransitKindName`, `@PlainText`, `@KoreanLatitude`, `@KoreanLongitude`, `@AccountEmail`, `@UserName`, `@Password`. DTO는 이 어노테이션만 붙이고 정규식을 다시 쓰지 않음 |
| `RequestBodyValidationAdvice`                  | **모든 `@RequestBody`를 컨트롤러에 넘기기 전에 검사**하는 미들웨어. 컨트롤러가 `@Valid`를 빠뜨려도 검사됨                                                                                                                                                   |
| 폼·경로·쿼리                                   | 폼 객체는 `@Valid` + `BindingResult`, 경로·쿼리 문자열은 제약 어노테이션(스프링 메서드 검증)                                                                                                                                                                |
| `GlobalExceptionHandler`                       | 검증 실패를 모두 400 `"입력값이 올바르지 않습니다."`로 응답. 보낸 값은 싣지 않고(S5) 필드 이름만 로그에 남김                                                                                                                                                |
| `InputValidationCoverageTests`                 | **등록된 모든 컨트롤러 메서드의 입력을 훑어**, 제약이 선언되지 않은 본문·폼·문자열 입력이 있으면 실패. 새 API가 검증을 빠뜨리면 빌드가 깨짐                                                                                                                 |
| `safe-html.js`의 `` html`...` ``               | 끼워 넣는 값을 모두 자동으로 이스케이프하는 태그 템플릿. 고정 마크업만 `raw()`                                                                                                                                                                              |
| `scripts/web-escape.test.js`                   | 모든 화면 스크립트의 `innerHTML`·`outerHTML`·`insertAdjacentHTML`·`document.write`가 ` html` ``이나 고정 문자열만 쓰는지, 템플릿이 `safe-html.js`를 먼저 불러오는지 검사                                                                                    |

컨트롤러에는 형식 검사를 직접 쓰지 않고, 날짜 범위(오늘부터 14일)·당일 예매·TAGO 재조회 같은 **업무 규칙만** 남깁니다.

**원칙**

1. **형식 검사:** 위 구조로 모든 입력의 형식·길이·범위를 검사합니다. 실패하면 400 `"입력값이 올바르지 않습니다."`이고, 보낸 값은 응답에 되돌려 싣지 않습니다(S5).
2. **서버 값으로 바꾸기:** 화면에 다시 보여 줄 문자열은 브라우저 값을 저장하지 않고 서버가 만듭니다. 장바구니·결제의 역 이름은 TAGO 마스터(`transit_place`)에서, 노선 표시는 TAGO 편 정보로 만듭니다. 운임도 TAGO 값입니다(S1).
   - 장바구니 목록(v2.6)은 DB 엔티티 대신 화면용 응답(`CartGroupView`)만 보냅니다. 이메일·내부 번호·운임 확인 표시는 내보내지 않고, 결제할 수 있는지와 막힌 이유도 서버가 정합니다. 이 판단은 결제 준비와 같은 `CartPayability`를 써서 화면과 서버가 어긋나지 않습니다(`CartFeatureTests`).
   - 주변정보(v2.7)는 분류를 정해진 값(`NearbyCategory` enum)으로, 좌표를 `@KoreanLatitude`·`@KoreanLongitude`로 받아 틀리면 카카오를 부르지 않고 400입니다. 응답(`NearbyPlaceView`)에는 좌표를 싣지 않고, 카카오맵 링크는 숫자 장소 ID로 서버가 만듭니다. 카카오 결과는 저장하지 않습니다(`HomeMenuFeatureTests`).
3. **출력 이스케이프:** HTML은 `` html`...` ``로만 만듭니다. 이벤트는 `addEventListener`로만 겁니다. v2.8부터 템플릿에도 인라인 이벤트 속성과 본문 있는 `<script>`가 없습니다(제출 전 확인은 `<form data-confirm>`).
4. **쓰지 않는 입구 없애기:** 화면에서 쓰지 않던 `/api/terminals`(TAGO 응답 XML을 그대로 넘김)를 지웠습니다.

**입력별 검사**

| 입력                                     | 검사                                                                                                                                                                                                                                                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 장바구니 담기·바로 결제 (`selectedLegs`) | 1-10개. `mode`는 TRAIN·EXPRESSBUS·AIRPLANE, `kind`는 TransitKind, `depId`·`arrId`는 영숫자 40자, `routeId`는 영숫자·`_-` 40자, `departureTime`은 숫자 12자리, `routePayment`는 1원 이상 100만 원 이하. 그다음 TAGO 재조회로 편·운임·당일 여부 확인. `route`·`startName`·`endName`은 저장하지 않음 |

**회귀 테스트**

- `InputValidationCoverageTests`: 모든 컨트롤러 입력에 검증이 선언됐는지(구조). 도입하자마자 `GET /register?error=` 쿼리의 빠진 제약을 찾아냈습니다. `PaymentRequest`의 제약을 지우면 결제 완료·실패 두 곳을 짚어 실패합니다.
- `InputValidationRegressionTests`:
  - 개발자도구로 바꾼 값(교통수단·ID·시각·운임 위조, 구간 0개·11개·null, 없는 역, UUID 아닌 묶음 번호, SQL·스크립트 모양의 결제 번호, 너무 긴 장소 이름·국외 좌표, 약한 비밀번호와 72바이트 초과 비밀번호)이 모두 400이거나 저장되지 않는지 확인합니다.

- `npm run test:web`(`scripts/web-escape.test.js`):
  - ` html` ``의 이스케이프(태그·속성·따옴표·백틱, 중첩, 배열, `raw`)를 확인합니다.
  - 모든 HTML 대입이 ` html` ``이나 고정 문자열인지, 인라인 이벤트에 값을 끼우지 않는지, 템플릿이 `safe-html.js`를 먼저 불러오는지, 템플릿에 인라인 이벤트 속성·본문 있는 `<script>`가 없는지 확인합니다.
  - 일반 템플릿 대입, 변수 대입, 문자열 이어 붙이기, 불러오는 순서를 하나씩 일부러 틀리게 바꿔 보면 각각 그 줄을 짚어 실패합니다.

## S11. 호출 횟수 제한과 비밀번호 대입 막기 (v2.9)

조회 기능을 비로그인에게 열면서, 외부 API 한도(TMAP 하루 10건)와 계정을 함께 지킵니다.

**API 호출 횟수** (`Common/RateLimit`, 한도 값은 `RateLimitPolicy`에만)

| 정책              | 대상 API                   | 로그인 사용자 | 비로그인(접속 IP 하나) | 비로그인 모두 합쳐 |
| ----------------- | -------------------------- | ------------- | ---------------------- | ------------------ |
| `ROUTE_SEARCH`    | 경로 검색(TMAP)            | 하루 10건     | 하루 3건               | 하루 5건           |
| `EXTERNAL_LOOKUP` | 장소 매칭·편 조회·주변정보 | 분당 60건     | 분당 20건, 하루 300건  | 없음               |
| `REGISTER`        | 회원가입                   | 해당 없음     | 시간당 10건            | 없음               |

- 컨트롤러 메서드에 `@RateLimited(정책)`을 붙이면 `RateLimitInterceptor`가 컨트롤러 전에 셉니다. 한도를 넘으면 컨트롤러와 외부 API를 부르지 않고 `429 {"error": 안내 문구}`와 `Retry-After`(초)를 돌려줍니다.
- 형식이 틀린 요청도 셉니다. 입력 검증보다 먼저 돌아서, 틀린 요청으로 한도 없이 두드릴 수 없습니다.
- 비로그인 합계 한도는 비로그인 사용자가 TMAP 한도를 회원 몫까지 쓰지 못하게 합니다.
- 시간 칸은 한국 시간으로 나눕니다. 하루 칸은 한국 자정에 다시 시작합니다(TMAP 일일 한도와 같은 기준).
- 회원가입은 폼 화면이라 서비스(`UserAccountService`)가 같은 정책으로 세고, 넘으면 폼에 안내 문구를 보입니다.
- **로그인 없이 여는 API는 `SecurityConfig.ANONYMOUS_API_PATHS`에 넣고 `@RateLimited`를 붙여야 합니다.** `RateLimitCoverageTests`가 등록된 모든 컨트롤러 메서드를 훑어, 공개 API에 제한이 없거나 목록에 있는데 컨트롤러가 없으면 실패합니다.

**비밀번호 대입** (`PasswordAttemptGuard`, 틀린 횟수만 셈)

- 로그인: 이메일마다 15분에 5번, 접속 IP 하나에서 15분에 20번 틀리면 그 15분 칸이 끝날 때까지 비밀번호를 확인하지 않고 `/login?locked`로 보냅니다. 맞는 비밀번호도 확인하지 않습니다.
  - 없는 이메일도 똑같이 셉니다. 대소문자·앞뒤 공백만 다른 이메일은 같은 이메일로 셉니다.
  - 잠김 안내에는 남은 시간을 싣지 않습니다(이메일마다 달라 잠긴 이메일을 알려 주게 되므로).
  - 로그인에 성공하면 그 이메일의 실패 횟수를 지웁니다. IP 실패 횟수는 지우지 않습니다(자기 계정으로 로그인해 다른 계정 대입 횟수를 되살리지 못하게).
- 마이페이지 비밀번호 변경의 현재 비밀번호: 계정마다 15분에 5번. 세션을 잠깐 빌린 사람이 대입하지 못하게 합니다.

**응답 시간차 막기**

로그인 시간의 대부분은 BCrypt 비교입니다. 없는 이메일에서 비교를 건너뛰면 응답이 빨라져, 시간만 재도 가입한 이메일을 골라낼 수 있습니다.

- 없는 이메일도 틀린 비밀번호와 같은 길을 탑니다. `AccountUserDetailsService`가 `UsernameNotFoundException`을 던지면, Spring Security(`DaoAuthenticationProvider`)가 같은 비용의 가짜 해시와 한 번 비교합니다. 다른 예외로 바꾸면 이 보호가 꺼집니다.
- 비교 자체는 BCrypt가 끝까지 다 보고 판정하므로, 비밀번호 앞부분이 맞을수록 빨라지는 차이는 없습니다.
- 잠긴 로그인(`?locked`)은 비교 없이 바로 돌려보냅니다. 있는 이메일과 없는 이메일이 똑같이 잠기므로 가입 여부는 드러나지 않습니다.
- 회원가입의 "이미 사용 중인 이메일" 안내는 문구로 가입 여부를 알려 주는 설계입니다(가입 화면에서 흔히 택하는 쪽). 대신 회원가입 횟수 제한으로 대량 조회를 막습니다.
- v2.9 실측(로컬 앱): 없는 이메일 0.38-0.40초, 있는 이메일·틀린 비밀번호 0.38-0.42초. 첫 요청만 가짜 해시를 만드느라 0.69초였습니다.

**로그인 뒤 돌아갈 화면** (`LoginRedirect`)

- 로그인 폼의 `next`는 `/home`, `/route`, `/compare`, `/nearby`(와 `?index=숫자`)만 받습니다. `https://...`, `//...` 같은 다른 사이트 주소나 그 밖의 경로는 무시하고 `/home`으로 보냅니다(열린 리다이렉트 방지).

**한계와 배포(v3) 때 할 일**

- 횟수는 서버 한 대의 메모리에만 있습니다. 서버를 다시 띄우면 처음부터 세고, 서버를 여러 대로 늘리면 Redis 같은 공용 저장소로 옮겨야 합니다.
- 키가 10만 개까지 차면(여러 IP로 채우는 공격) 새 클라이언트를 1분 동안 거절합니다. 외부 API 한도를 지키는 쪽을 골랐습니다.
- 시간 칸을 고정해 나누므로, 칸 경계 앞뒤로 몰아 쓰면 짧은 시간에 한도의 두 배까지 쓸 수 있습니다.
- 비로그인 사용자는 접속 IP로 구분합니다. 리버스 프록시 뒤에 두면 모든 요청이 프록시 IP로 보이므로, 믿을 수 있는 프록시의 `X-Forwarded-For`만 쓰도록 설정해야 합니다(`server.forward-headers-strategy`). 같은 IP(회사·학교 공유기)를 쓰는 사람들은 한도를 함께 씁니다.

**회귀 테스트**

- `RateLimitRegressionTests`(시계를 고정):
  - 비로그인 경로 검색 3건 뒤 429와 `Retry-After`, TMAP 호출은 3번뿐인지 확인합니다.
  - 비로그인 합계 5건, 회원 10건과 비로그인 합계에 막히지 않는지, 한국 자정에 다시 세는지 확인합니다.
  - 조회 API 합계 분당 20건(형식이 틀린 요청 포함)을 확인합니다.
  - 로그인 5번 실패 뒤에는 맞는 비밀번호도 잠기는지, 없는 이메일·대소문자 변형, IP 20번, 성공 뒤 초기화, `next` 허용·거부를 확인합니다.
  - 비밀번호 변경 5번 실패 뒤 잠김, 회원가입 11번째 거절을 확인합니다.
- `LoginTimingRegressionTests`: 없는 이메일과 틀린 비밀번호가 모두 BCrypt 비교를 한 번 하는지(비밀번호 인코더 호출 횟수), 응답 시간 중앙값 비율이 0.5-2배 안인지, 잠긴 로그인은 두 경우 모두 비교하지 않는지 확인합니다. 없는 계정을 다른 예외로 알리게 바꾸면 두 테스트가 실패합니다(일부러 바꿔 확인).
- `RateLimitCoverageTests`: 공개 API에서 `@RateLimited`를 하나 지우면 그 메서드를 짚어 실패합니다(일부러 지워 확인).
- `RateLimiterTests`: 시간 칸 끝, 한국 자정 기준, 남은 시간 문구.

## S12. 관리자 (v2.11)

**누가 관리자인가**

- `.env`의 `ADMIN_EMAIL` 계정 한 명입니다. 앱이 뜰 때 그 계정만 관리자로 지정하고, 다른 관리자 계정은 일반 회원으로 내립니다(`AdminBootstrap`).
- 화면이나 API로는 관리자를 만들 수 없습니다. 서버 설정을 바꿀 수 있는 사람만 관리자를 정합니다.

**2단계 인증 (TOTP, RFC 6238)**

- 관리자 계정이 비밀번호로 로그인하면 `ROLE_USER`와 `ROLE_ADMIN_PENDING`만 받습니다. 이때 열리는 관리자 화면은 OTP 화면(`/admin/otp`)뿐입니다. 다른 관리자 주소를 열면 OTP 화면으로 보냅니다.
- 인증 앱(Google Authenticator 등)의 6자리 번호를 확인해야 `ROLE_ADMIN`을 더합니다. 이때 세션 ID를 바꾸고(세션 고정 방지), 관리자 세션 유지 시간을 10분으로 줄입니다.
- 무료이고 외부 서비스·도메인·문자 발송이 필요 없습니다. 서버와 앱이 같은 비밀값과 현재 시각으로 각자 계산합니다. 시계 차이는 앞뒤 30초까지 받습니다.
- **같은 번호는 두 번 받지 않습니다**(마지막으로 받은 시간 칸 저장). 틀리면 계정마다 15분에 5번까지입니다(`PasswordAttemptGuard`). 번호 비교는 끝까지 다 봅니다.
- 비밀값은 AES-256-GCM으로 암호화해 저장합니다. 키(`ADMIN_OTP_KEY`)는 DB 밖(.env)에 둡니다. 키가 없으면 관리자 화면을 열지 않습니다(fail closed).
- 등록 QR은 서버에서 SVG로 그립니다. 외부 QR 생성 서비스에 비밀값을 보내지 않습니다.
- **복구 코드:** 등록할 때 8개를 한 번만 보여 주고 BCrypt 해시만 저장합니다. 하나씩 한 번만 쓸 수 있습니다.

**관리자 화면에서 지키는 것**

- 계정 목록·상세의 이메일·이름은 가려서 보여 줍니다(`k***@gmail.com`, `김**`).
- **실제 이메일·이름은 계정 하나씩만 엽니다.** 계정 상세에서 열람 이유와 지금 OTP 번호를 함께 받고, 확인되면 그 응답에서만 보여 줍니다. 세션·DB에 남기지 않아 새로고침하면 다시 가려집니다. 감사 로그에 "개인정보 열람"으로 이유와 함께 남습니다.
  - 열람은 관리자 한 명당 1시간 10건, 하루 30건까지입니다(`RateLimitPolicy.ADMIN_PII_REVEAL`). 세션을 빼앗겨도 한 명씩 열어 회원 명단을 모으지 못하게 늦춥니다. 횟수는 OTP 확인보다 먼저 세어, 틀린 번호도 한 번으로 셉니다.
  - 여러 계정을 한 번에 펼치거나 내려받는 기능은 두지 않습니다.
- 계정 정지·정지 해제·로그인 잠금 풀기는 **지금 OTP 번호를 다시 받아야** 합니다(`stepUp`). 세션을 잠깐 빌린 사람이 할 수 없습니다.
- 관리자 계정은 정지할 수 없습니다.
- 정지하면 그 계정의 로그인 세션을 바로 끝냅니다(세션 등록부). 정지된 계정은 비밀번호를 맞혀도 로그인되지 않고 "이용 정지" 안내를 받습니다. 안내는 비밀번호를 맞힌 사람에게만 보입니다.
- 사용자가 예매 내역에서 숨긴 결제(S4)는 관리자 계정 상세에서 볼 수 있습니다(문의 대응).
- 모든 관리자 POST는 CSRF 토큰이 필요합니다(S3).

**감사 로그 (`admin_audit_log`)**

- OTP 등록·확인·실패, 복구 코드 사용, 계정 목록·상세 조회, 개인정보 열람(이유 포함), 정지·해제·잠금 풀기, 재확인 실패를 남깁니다. 누가·언제·어디서(IP)·누구에게(대상 계정 ID)를 기록합니다. 검색어는 길이만 남깁니다.
- **추가만 합니다.** 엔티티에 수정자가 없고, 저장소는 `JpaRepository`가 아닌 `Repository`로 저장·조회만 엽니다. 실패한 시도도 남도록 별도 트랜잭션(`REQUIRES_NEW`)으로 저장합니다.

**배포(v3) 때 할 일**

- `/admin`을 정해 둔 IP에서만 열기(리버스 프록시)
- 패스키(WebAuthn)를 추가 수단으로 검토 (등록 정보가 도메인에 묶이므로 실제 도메인이 생긴 뒤)

**회귀 테스트**

- `AdminSecurityRegressionTests`: 실제 로그인 폼으로 들어가 OTP를 등록·확인합니다(시계 고정). 확인하는 것:
  - 비로그인·일반 회원은 관리자 화면을 못 엶, 비밀번호만 맞힌 관리자는 OTP 화면만 열림
  - OTP 확인 뒤 세션 ID 변경·10분 유지
  - 같은 번호 재사용 거절, 5번 실패 뒤 맞는 번호도 잠김, 복구 코드 한 번만
  - 비밀값 암호화 저장, CSRF
  - 이메일·이름 가림, 틀린 재확인 번호로는 정지되지 않음, 정지 즉시 세션 종료와 로그인 차단, 관리자 정지 거절, 숨긴 결제 표시
  - 개인정보 열람: 틀린 번호·이유 없음은 거절, 성공하면 감사 로그에 남고 다시 열면 가려짐, 맞는 번호여도 1시간 11번째는 거절
  - 감사 로그가 추가만 되는지(구조)
- 일부러 깨 보기: 비밀번호 로그인만으로 `ROLE_ADMIN`을 주게 바꾸면 11개 실패, 정지에서 OTP 재확인을 빼면 정지 테스트가 실패했습니다. 열람 횟수 한도를 빼면 한도 테스트가 실패했습니다.
- `TotpTests`: RFC 6238 부록 B 시험 값, 시계 차이·재사용, Base32(RFC 4648), 암호화 왕복·변조 감지·키 길이, 가림 규칙
- `AdminBootstrapTests`: 지정 이메일만 관리자, 비우거나 없는 이메일이면 관리자 없음
- 테스트는 감사 로그를 별도 트랜잭션에서 읽고 지웁니다(MySQL 스냅샷 때문에 테스트 트랜잭션에서는 나중에 커밋된 행이 안 보일 수 있음).
